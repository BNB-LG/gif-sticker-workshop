# 手工制作与核验教程

## 1. 先锁定角色，不急着做八张

用你自己拥有或获得许可的角色参考。先记录头身比例、脸部特征、颜色、配件与位置，并说明哪些必须保持。没有图片时，可以先写文字锚点；这不等于已经完成角色设计或通过撞形检查。

本仓库的海獭规划使用新写的文字锚点，尚未生成。既有 GIF 只是审计例子，不自动成为这份规划的角色参考。

## 2. 动作要能逐帧说清楚

先选一个挥手和一个点头试样，确认后才考虑余下动作。一个动作通常包括起势、主要动作、放松回位；这是创作建议，不是平台帧数规定。

下面是原创的手工提示词例子，需先获得生成授权，再交给实际支持原生 GIF 的工具：

> 根据已确认的角色锚点，制作同一只原创海獭的连续动作 GIF。固定镜头，完整保留头、身体和双爪。开始时双爪自然放在胸前；右爪抬起，手腕轻摆两次，同时眉眼变得精神；右爪放回，肩部自然松下来，最后回到初始姿态。左腕的小配件始终在左侧。关节和表情要随动作变化，不要只移动或旋转整张静态画。使用清晰的纯色背景，不加文字、商标、水印或其他角色。保存原始 GIF 下载文件。

若界面只返回静态图，标记“GIF 输出未获得”，停止扩批。不要改后缀，不用程序加摇摆来补交，也不要将 sprite sheet 后期拼合描述为接口直接输出的原生 GIF。真正的后期动画可以另做，但必须标明方法并重新获得用户接受。

## 3. 保留生成证据

记录工具/产品显示名称、生成日期、实际可见的模型标识、提示词版本、下载文件 SHA256。没有模型标识就填 `null`。请求里写了模型名也不单独证明实际返回的模型身份；保留可用响应证据，不能杜撰响应没有的字段。

公开仓库只保留已脱敏的来源说明，不放账号、聊天 URL、个人绝对路径、访问令牌或未经许可的参考图。源文件和报告分开存储，不覆盖下载文件。

## 4. 跑离线审计

```sh
python3 -B scripts/audit_gif.py audit examples/otter-wave-gif-test.gif --out output/check-01
```

检查 JSON：实际 GIF、至少两帧、至少两张不同画面、每帧有效时长、完整解码。loop 不无限时会警告，但这不是所有平台通用的失败条件。数字正常仅进入视觉审查阶段。

有浏览器使用权限时再打开 HTML。先看原始 GIF 播放，再暂停解码帧，逐帧查五官、手爪和配件；最后看末帧到首帧。原尺寸 PNG 用来检查联系图缩小后可能藏住的缺陷。没有浏览器权限时仍可交付 HTML，但明确写“播放未验收”。

建议留一个人工记录：文件 SHA256、审查人、审查日期、角色一致性、动作完整性、残影/裁切、首尾衔接、结论与缺陷帧号。不要从机器 `pass` 自动填“人工通过”。

## 5. 扩批和投稿是两道后续关卡

只有用户接受试样才扩批，别将 8 条规划说成 8 个成品。每个动作各自有原文件、报告、人工结论。对于尺寸或体积优化，应保留原文件、另存衍生版本并重新审计，不默认套用任何未经核实的平台数字。

微信投稿需要另行核实官方页面及适用入口：聊天添加和表情开放平台投稿不是同一流程。补齐 `profiles/wechat.pending.json` 所列信息、建立经过复核的规则检查器、准备权利材料并取得用户明确上传授权之后，才可进入投稿准备；平台最终审核仍不能由本工具替代。
